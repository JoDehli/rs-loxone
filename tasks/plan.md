# Implementation Plan: rs-loxone (protocol, auth, transport)

## Overview

Build the low-level async Rust client for the Loxone Miniserver in three
modules, in dependency order: `protocol` (pure parsing), `auth` (crypto and token
logic, no I/O), `transport` (HTTP bootstrap, WebSocket, TLS, keepalive). Each
module has an approved spec: `SPEC-protocol.md`, `SPEC-auth.md`,
`SPEC-transport.md`. The Python library `pyloxone-api-main/` is the behaviour
reference; the Loxone PDF (V17.0) is the protocol reference.

Modules `session`, `supervisor` and `cli-and-crate` are out of scope for this
plan. They get their own specs and plans after these three are built.

Tasks are recorded in `tasks/todo.md` (the default task list target).

## Architecture Decisions

- **Three modules, pure first.** `protocol` and `auth` do no I/O, so they can be
  tested with fixed bytes and fixed keys. Only `transport` touches sockets.
- **Tokio** for the async runtime (approved). `transport` is the only module that
  uses it.
- **RustCrypto** for all crypto (approved). It replaces PyCryptodome.
- **Python is the byte-level reference.** Known-answer tests are generated by the
  Python helpers on fixed inputs. Where the PDF differs, the spec decision applies:
  - killtoken sends the token hash (PDF).
  - `nextSalt` on every command (PDF).
  - AES PKCS#7 padding (Python, tested live).
  - UUID text form `8-4-4-16` (Python and `LoxAPP3.json`).
  - Subprotocol `remotecontrol` (PDF).
- **Encryption policy:** `enc` is always on, for Gen 1 and Gen 2 (transport spec, decision 7).
- **Injected clock and RNG** in `auth` and `transport`, so tests are deterministic and
  need no sleeps.
- **Errors are typed per module** (`ProtocolError`, `AuthError`, `TransportError`).
  No panics on network or device input.

## Dependency Graph

```
T0 scaffold
 ├── P1 header ─┐
 ├── P2 UUID ───┼── P3 value states
 │              └── P4 text states
 ├── P5 LL response ──┬── P6 frame dispatch (needs P1–P5)
 │                    └── A6 reply parsing
 ├── A1 hashes ─────── A5 command builders (needs A1–A4, A6)
 ├── A2 session key
 ├── A3 enc cipher
 ├── A4 token state ──┘
 ├── Tr1 URL ──┬── Tr3 HTTP bootstrap (needs Tr1, Tr2, P5)
 │             └── Tr2 errors + retry ──┘
 ├── Tr4 TLS (needs Tr1, Tr2)
 ├── Tr5 WebSocket (needs Tr1, Tr2, Tr4)
 └── Tr6 keepalive + watchdog (needs Tr5)
```

Parallel: `protocol` (P1–P5) and `auth` (A1–A4) can run in parallel after T0.
Transport starts after T0 and the protocol LL parser (P5).

## Risks and Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| No live Gen 2 Miniserver; Gen 2 is tested only against mocks and a local TLS server | High | Mock tests for TLS and CloudDNS paths. Live check on a Gen 2 device when available. |
| `killtoken` with a hash is untested on the device; the Python code says the hash gets 401 | Medium | Kill is best effort; log the reply. Live test on Gen 1 before relying on it. |
| Python-vs-PDF differences (salt rotation, subprotocol, AES padding) | Medium | Each is a recorded decision. Live check of the first encrypted command and the first connect. |
| RustCrypto API differences from PyCryptodome (RSA PKCS#1 v1.5 encryption, CBC padding) | Medium | Known-answer tests from Python for every primitive. Round-trip tests. |
| Structure file (`LoxAPP3.json`) is several MB and parsing blocks the runtime | Medium | Transport returns bytes; the caller parses with `spawn_blocking` (session spec). |
| Certificate verification against public CAs only (no Loxone root) | Medium | `ca_file` option kept. Add the Loxone root when available. |
| Scope creep into `session` | Medium | `session`, `supervisor` and `cli-and-crate` have their own specs and plans. |

## Open Questions

- Live Gen 2 test device: none. The user has only a Gen 1. Gen 2 is verified by mocks and the local TLS test server only, so the Gen 2 claim stays unverified on real hardware until a Gen 2 device is available.
- Live test window on the Gen 1: can I run the first connect, `getkey2`, an encrypted
  command and `killtoken` against your device? These can change your Miniserver's
  session state, so I want your go-ahead first.
- Rust toolchain: the crate uses edition 2024. Which stable toolchain version should
  the CI target? (Currently the local one is used.)
